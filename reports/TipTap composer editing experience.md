# Lor's composer jank lives in glue code

Lor does not need a new editor. Almost every janky moment in the web and Tauri composer comes from about a dozen integration choices in Lor's own code around TipTap 3.32.2, and each one has a fix inside TipTap. The worst are correctness bugs. The edit box loads stored markdown as HTML, so **saving an edit, even with no changes, collapses every line break, turns formatting into literal asterisks and breaks mentions**. A leftover `++` regex **deletes all text between any two `++`**, so "C++" and `i++` inside code are lost. Harness commands such as `/pr_comments` are stored escaped, so Claude Code does not recognize them. Next come keyboard traps. Enter-to-send lives in `editorProps.handleKeyDown`, which ProseMirror runs before every plugin. As a result **a code block cannot get a second line from the keyboard**, line-start shortcuts (`- `, `1. `, a triple-backtick fence) stop working after the first Shift+Enter, and "@l" + Enter, meant for Lor, inserts **@channel**. Then performance: every keystroke and every Lor stream frame re-renders the 1,838-line `MessageInput` and triggers about four ProseMirror view updates, because inline options defeat TipTap's memoization. The best composers (Slack, Discord, Campsite, Plane, Campfire) share one model, and it fits Lor's constraints. Enter sends unless a menu or an IME composition owns the key. Shift+Enter runs the editor's structural Enter chain. Cmd+Enter always sends. Pasted markdown is parsed, and pastes into code stay plain. The plan at the end does this in fourteen ordered chunks of at most about 400 changed lines. It starts with a lockfile bump and the data-loss fixes. Every finding comes from reading the code and the installed TipTap/ProseMirror sources at `696ee2ee`. Nothing was profiled or run in WKWebView, so the costs are unmeasured and several WebKit behaviors need manual QA.

## Three integration bugs rewrite or delete what people type

The most serious defect is in the message edit box. It calls `useEditor({ content: withLinearIssueNodes(initialContent) })` with no `contentType: "markdown"` ([message-edit-input.tsx:79](../apps/web/src/components/chat/message-edit-input.tsx)). `@tiptap/markdown` parses markdown only when that option is set ([Extension.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/markdown/src/Extension.ts)). So stored markdown goes through the HTML parser, which **collapses every run of whitespace, newlines included, to a single space** ([from_dom.ts](https://github.com/ProseMirror/prosemirror-model/blob/master/src/from_dom.ts)). `<@uuid>` is not a valid tag start, so it stays as literal text. On save the serializer escapes everything again. Take a message like `**Ship it** <@uuid>`, followed by two bullets. It reopens as one flat line and saves as `\*\*Ship it\*\* &lt;@uuid&gt; - a - b`, which shows literal asterisks and a raw ID and gets an "(edited)" tag. The "unchanged" check compares the re-serialized text with the original, so **even a no-op save rewrites the message** ([message-edit-input.tsx:100-116](../apps/web/src/components/chat/message-edit-input.tsx)). The repo already has the right pattern: `instructions-section.tsx` loads and saves markdown correctly ([instructions-section.tsx:114-137](../apps/web/src/components/workspace/instructions-section.tsx)).

The second bug is in send-time post-processing. `storedText` runs `.replace(/\+\+([\s\S]+?)\+\+/g, "$1")`. That regex was written for an older TipTap that wrapped unknown marks in `++` ([editor-utils.ts:44-47](../apps/web/src/lib/editor-utils.ts)). In 3.32.2 nothing emits `++`: Link serializes as `[text](href)` ([link.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/extension-link/src/link.ts)). So "C++ is fine, but C++ templates…" is stored as "C is fine, but C templates…", and `for (i=0;i<n;i++) { j++ }` loses its increments. Because `[\s\S]` spans lines, two `++` in different blocks also delete everything between them. The other regexes in the same function also run inside code. The `[x](x)` to `x` rewrite changes markdown examples in code blocks. The mention regex stops at the first `]`, so a label like "Bob [Eng]" leaves residue ([editor-utils.ts:27-60](../apps/web/src/lib/editor-utils.ts)). All of this regex layer exists to patch serializer output after the fact. TipTap 3 lets each node own its markdown through `renderMarkdown`, and Mention already uses `createInlineMarkdownSpec` ([mention.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/extension-mention/src/mention.ts)). So the fix is to emit `<@id>` and bare URLs at node level and delete the regexes.

The third problem is escaping. Since 3.25.0, `getMarkdown()` backslash-escapes `` \ ` * _ [ ] ~ `` and HTML-encodes `& < >` in all non-code text ([MarkdownManager.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/markdown/src/MarkdownManager.ts)). That is right for the Streamdown renderer. It is wrong for anything that reads the content as plain text. A harness skill named `/pr_comments` is stored as `/pr\_comments`. The worker passes the raw content to `parseHarnessCommand`, which matches names exactly, so **the command silently becomes an ordinary prompt** ([lor-respond.ts:891-905](../apps/worker/src/jobs/lor-respond.ts); [harness-commands.ts:292-297](../packages/lor/src/harness-commands.ts)). Lor's own prompt sees `a &amp; b` and `x &gt; 5`. Upstream knows the escaper breaks round trips: issue [#8519](https://github.com/ueberdosis/tiptap/issues/8519) and its fix PR #8520 are still open, and neither 3.32.3 nor 3.33.0 changes this ([TipTap releases](https://github.com/ueberdosis/tiptap/releases)). Keep TipTap's escaping for rendering, and unescape deliberately for plain-text consumers, starting with harness commands. Which notification, preview and search surfaces show raw `message.content` was not audited.

Several smaller losses compound these. StarterKit 3 bundles Underline, which serializes as `<u>`. The sanitize schema that Streamdown extends has no `u` tag, so **Cmd+U formatting disappears after send** ([starter-kit.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/starter-kit/src/starter-kit.ts)). Whether Streamdown keeps the inner text was not verified at runtime. A hard break serializes as two spaces plus a newline. Two Shift+Enters therefore produce a whitespace-only line, which CommonMark reads as a paragraph break, so blank lines shrink or collapse after send ([TipTap #8478](https://github.com/ueberdosis/tiptap/issues/8478), open). `defaultLanguage: "plaintext"` writes `plaintext` into every fence ([message-input.tsx:840-842](../apps/web/src/components/chat/composer/message-input.tsx)). The post-send `clearContent` is an ordinary undo step, so **Cmd+Z after sending restores the sent text**, and one Enter sends it again. The channel and DM composers have no React `key`, so one editor and one undo stack serve every channel ([$channelId.tsx:633-634](../apps/web/src/routes/_authenticated/$workspaceSlug/$channelId.tsx); [$dmId.tsx:280-281](../apps/web/src/routes/_authenticated/dms/$dmId.tsx)). After a channel switch, Cmd+Z pulls the previous channel's draft into this channel and saves it as this channel's draft.

## Enter-to-send pre-empts every structural key TipTap ships

ProseMirror's `someProp` checks direct view props before any plugin ([prosemirror-view index.ts](https://github.com/ProseMirror/prosemirror-view/blob/master/src/index.ts)). TipTap passes `editorProps` as direct props and adds the extension plugins later ([Editor.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/core/src/Editor.ts)). So the composer's `handleKeyDown` runs before the Suggestion, ListItem, ListKeymap, CodeBlock, HardBreak and core keymaps ([message-input.tsx:876-897](../apps/web/src/components/chat/composer/message-input.tsx)). It consumes Enter everywhere, with no code-block check. Shift+Enter falls through to HardBreak, whose `setHardBreak` calls `exitCode()` first ([hard-break.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/extension-hard-break/src/hard-break.ts)). `exitCode` inserts a paragraph after the whole code node ([commands.ts](https://github.com/ProseMirror/prosemirror-commands/blob/master/src/commands.ts)). The result: **inside a code block, Enter sends half a snippet and Shift+Enter throws the caret below the block, even from the middle of it.** The only way to write multi-line code is to paste it. Typing a triple-backtick fence and pressing Enter sends the literal backticks, because the fence rule needs a trailing space and the InputRule Enter path never runs.

The same design breaks markdown shortcuts. Input rules match text from the start of the textblock. A hard break contributes the sentinel `%leaf%`, and the list, fence, bold, italic and strike rules are all anchored to `^` or `(?:^|\s)` ([getTextContentFromNodes.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/core/src/helpers/getTextContentFromNodes.ts); [InputRule.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/core/src/InputRule.ts)). Every multi-line message is one paragraph joined by hard breaks, so **`- `, `1. `, `**`, `~~` and fences fail silently on every line after the first**. Only inline code still converts. Worse, the dashed lines stay plain in the composer but render as a real list after send, because a CommonMark list can interrupt a paragraph. That mismatch is the core WYSIWYG break, and it is covered in the next section.

The suggestion menus add a second class of traps. The composer does not read suggestion state from the plugins. It runs `document.querySelector(SUGGESTION_MENU_SELECTOR)` across the whole document. The popup renders even when a query has no results ("No matches", "No commands") and still carries the open-menu attribute. The composer then skips sending, the list declines the key, and **Enter after "check /tmp" or "ask @nobody" inserts a newline instead of sending** ([message-input.tsx:307-331](../apps/web/src/components/chat/composer/message-input.tsx); [mention-suggestion-list.tsx:67](../apps/web/src/components/chat/composer/mention-suggestion-list.tsx)). The Suggestion plugin has no blur handling. Lor's hand-built popup manager also skips TipTap's outside-click dismissal, so an "@" menu left open in the channel composer blocks Enter in the thread composer ([state.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/suggestion/src/plugin/state.ts)). Shift+Enter and Cmd+Enter with a menu open select the highlighted item, because the lists check only `event.key === "Enter"`. Tab on a first bullet or in a code block moves focus out of the editor. `sinkListItem` fails on a first item, and `enableTabIndentation` is off ([code-block.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/extension-code-block/src/code-block.ts)). Cmd+Shift+S toggles strikethrough and also opens the thread subscribers picker, whose window listener ignores `defaultPrevented` ([thread-subscribers.tsx:134-145](../apps/web/src/components/chat/thread-subscribers.tsx)).

The edit box handles keys a third way: capture-phase `keydown` listeners on `view.dom`, which run before ProseMirror sees the event ([message-edit-input.tsx:118-156](../apps/web/src/components/chat/message-edit-input.tsx)). **Escape discards the whole edit even when the user only meant to close the @ menu.** Enter also skips ProseMirror's Safari IME guard. That guard suppresses key handlers for 500 ms after `compositionend` because "On Safari, when Enter is pressed, compositionend and keydown events are emitted" ([prosemirror-view input.ts](https://github.com/ProseMirror/prosemirror-view/blob/master/src/input.ts)). ProseMirror identifies Safari by `navigator.vendor`, so the guard also covers Tauri's WKWebView. In the edit box, an Enter that confirms a Japanese or Chinese candidate can therefore save early. This is likely from the code, but it was not reproduced. This bug class is common: reporters call it "non-standard behavior compared to … Slack, Discord, and Teams" ([claude-code#8455](https://github.com/anthropics/claude-code/issues/8455)).

Mentions have the most dangerous default. Channel composers put @channel, @here and @everyone first, preselect index 0, and filter by substring on label or search text. "channel" contains l, e, a, n, h and c. So **"@" + Enter, "@l" + Enter or "@e" + Enter inserts a mention that notifies the whole channel** ([mention-suggestion-list.tsx:33-44](../apps/web/src/components/chat/composer/mention-suggestion-list.tsx); [broadcast-mentions.ts](../apps/web/src/lib/broadcast-mentions.ts)). Mention's `deleteTriggerWithBackspace` defaults to false. So Backspace on a mention turns it back into "@" and reopens the menu, and a stray Enter re-inserts the top result ([mention.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/extension-mention/src/mention.ts)). The popup always opens above the caret and never flips, and the active row is never scrolled into view. TipTap 3.32's Suggestion already ships `props.mount()`, which handles Floating UI placement, flip, outside-click dismissal and repositioning on scroll and resize. Its docs call it "the recommended, default way to render a suggestion popup" ([suggestion types.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/suggestion/src/types.ts)).

The best composers have converged on a model that fixes all of this and respects Lor's Enter-sends rule:

| Key | Slack | Discord / Teams | Campsite, Plane (TipTap) | Linear, GitHub | Lor today | Lor target |
|---|---|---|---|---|---|---|
| Enter | Sends | Sends | Sends unless a menu is open | New line; Cmd+Enter posts | Sends, even in code; inserts a newline when a menu shows "No matches" | Sends unless a menu with results is open or an IME is composing |
| Shift+Enter | New line; next bullet in a list | New line | TipTap's Enter chain: code newline, list split, lift empty, split block | Line break | Hard break; in code, jumps below the block | Same structural chain |
| Cmd+Enter | Sends when Enter is set to newline | Teams: sends from the expanded box | n/a | Submits | Sends (in sessions: send and stay) | Unchanged |
| Tab | Indents lists, five levels | n/a | n/a | GitHub: moves focus | Leaves the editor on a first bullet or in code | Indent or swallow in lists, indent in code, focus elsewhere |
| Escape | n/a | Closes menus first, then focuses the input | Campsite blurs the editor | Linear: closes the prompt, then blurs | Does nothing in the composer; discards the edit in the edit box | Menu, then reply, then edit, then blur |
| Up arrow, empty box | Edits last message | Discord edits last message | n/a | n/a | Nothing | Edit last own message |

Slack documents Shift+Enter for a new line and Up arrow to edit the last message ([Slack shortcuts](https://slack.com/help/articles/201374536-Slack-keyboard-shortcuts)). A tested walkthrough adds that Shift+Enter makes a new bullet in a list and Backspace on an empty bullet ends the list ([slack.green](https://slack.green/en/blog/how-to-make-bullet-points-in-slack)). Campsite, an open-source TipTap chat app, binds Shift+Enter to `newlineInCode → createParagraphNear → liftEmptyBlock → splitBlock`, "mirroring TipTap enter key handler" ([Campsite EnterSubmit.ts](https://github.com/campsite/campsite/blob/main/packages/editor/src/extensions/EnterSubmit.ts)). Plane adds `splitListItem` to the chain, and lets open dropdowns register in editor storage so that Enter falls through to them ([Plane enter-key.ts](https://github.com/makeplane/plane/blob/preview/packages/editor/src/extensions/enter-key.ts)). Campfire never sends while a prompt is open or during composition ([once-campfire composer_controller.js](https://github.com/basecamp/once-campfire/blob/main/app/javascript/controllers/composer_controller.js)). Discord's Escape closes any open menu before it does anything else ([Discord keyboard navigation](https://discord.com/blog/how-to-navigate-discord-using-only-your-keyboard)). Linear and GitHub post with Cmd/Ctrl+Enter ([Linear docs](https://linear.app/docs/comment-on-issues); [GitHub shortcuts](https://docs.github.com/en/get-started/accessibility/keyboard-shortcuts)). Two precedents conflict with Lor's constraint, and the plan rejects both. Slack has an opt-in where Enter adds lines inside a fenced block and Shift+Enter sends. Users call that inversion confusing, and one proposes the block "should simply never send on (shift+)enter" ([HN thread](https://news.ycombinator.com/item?id=47741915)). Teams and Campfire flip Enter to a newline in an expanded mode, which would break "Enter sends". The plan keeps Enter as send everywhere and makes Shift+Enter add a code line, so nothing is inverted. The implementation is one `ComposerKeymap` extension, shared by the composer and the edit box, that reads suggestion state from the plugin keys. Inside ProseMirror's keydown path it inherits the IME guard for free ([Plane PR #8893](https://github.com/makeplane/plane/pull/8893)).

## The composer previews one message and stores another

Block markdown typed as plain text gets formatted after send. The editor disables headings, blockquotes and horizontal rules ([message-input.tsx:833-835](../apps/web/src/components/chat/composer/message-input.tsx)). But the serializer escapes only inline characters, and the message renderer styles headings, rules, tables and quotes ([globals.css:362-381](../packages/ui/src/styles/globals.css)). So "# Title", "> quote", "---", "1) step" and pipe tables show as plain text in the composer and **land formatted in the channel**. The principle that removes this is "what looks literal in the composer stays literal". Escape any line-leading block marker the editor cannot display, outside code. Separately, decide whether quotes earn a place in the schema. Slack, Discord and GitHub all support them ([Markdown Guide: Discord](https://www.markdownguide.org/tools/discord/); [Slack: Format your messages](https://slack.com/help/articles/202288908-Format-your-messages)).

Paste half-converts. With no HTML on the clipboard, ProseMirror splits text on `/(?:\r\n?|\n)+/` into paragraphs, so **blank lines disappear** ([clipboard.ts](https://github.com/ProseMirror/prosemirror-view/blob/master/src/clipboard.ts)). TipTap's mark paste rules convert `**b**` and `` `c` ``. `@tiptap/markdown` has no paste handling at all ([Markdown examples](https://tiptap.dev/docs/editor/markdown/examples)). The triple backticks of a pasted fence are escaped on send, so **pasted fenced code renders as double-spaced paragraphs**. Code copied from an IDE becomes indented paragraphs. TipTap makes a code block only when VS Code's `vscode-editor-data` MIME type is readable, and WKWebView probably does not expose that Chromium-private type (unverified). Rich HTML loses its headings and quotes. Underline survives into the editor and then vanishes. A paste over 4,000 characters silently becomes `pasted-text.txt` ([message-input.tsx:108-112, 898-917](../apps/web/src/components/chat/composer/message-input.tsx)). A connector URL pasted into a code block becomes a chip, because that handler lacks the code-context check that LinearIssue and RepoFileChip have ([connector-chip.tsx:137-149](../apps/web/src/components/chat/composer/connector-chip.tsx)).

The industry is still settling this, and AI products have learned the hardest lessons. A dated test found that Slack began formatting pasted markdown, tables included, between September 28 and October 27, 2026 ([slack.green](https://slack.green/en/blog/slack-markdown-not-working)). Linear converts pasted markdown "automatically" ([Linear editor docs](https://linear.app/docs/editor)). Outline's ProseMirror paste handler is the most complete public reference. In order, it pastes plain into code, passes ProseMirror and **Claude.ai** HTML (`font-claude-response-body`) to the HTML parser, handles single URLs, turns VS Code language pastes into code blocks, and parses text as markdown only when an `isMarkdown` signal count clears a threshold ([Outline PasteHandler.tsx](https://github.com/outline/outline/blob/main/app/editor/extensions/PasteHandler.tsx); [isMarkdown.ts](https://github.com/outline/outline/blob/main/shared/editor/lib/isMarkdown.ts)). Campsite uses the same order and honors Shift for plain paste ([Campsite PasteHandler.ts](https://github.com/campsite/campsite/blob/main/packages/editor/src/extensions/PasteHandler.ts)). ChatGPT shows the risk of overdoing it. After it moved to live rich-text conversion, users asked for a plain-text composer, because code, JSON and paths turned into structure; OpenAI said it has "no timeline" ([OpenAI community](https://community.openai.com/t/add-a-plain-text-composer-option-for-chatgpt-and-codex/1390698)). Its forced large-paste attachments caused months of complaints until "Show in text field" gave a way back ([devicebase](https://devicebase.net/en/openai-chatgpt/updates/large-pastes-are-now-handled-as-attachments/908)). For Lor this means: convert only on a strong markdown signal, never convert inside code, leave Cmd+Shift+V plain (ProseMirror already treats a Shift-held paste as plain text), and put an undo on the large-paste attachment.

The look also changes at the moment of sending. In a channel, line height goes from 20 px to 21 px and real paragraphs gain 6 px gaps. In a session it tightens from 24 px to **22.5 px**, although `message-item` tries to pin 24 px. The cause is that the `.message-markdown .prose` rules in globals.css sit outside any cascade layer, and unlayered rules beat Tailwind's layered utilities ([globals.css:199-260, 309-341](../packages/ui/src/styles/globals.css); [message-item.tsx:764-767](../apps/web/src/components/chat/message-item.tsx)). Bold drops from 700 to 550. Links change from violet, underlined only on hover, to foreground with an underline ([nexus-ui/message.tsx:34-36](../packages/ui/src/components/nexus-ui/message.tsx)). Inline code loses a violet tint that the stylesheet itself says "read like an @mention" ([globals.css:412-434](../packages/ui/src/styles/globals.css)). Code blocks wrap in the composer, because TipTap injects `.ProseMirror pre { white-space: pre-wrap }`, but scroll with line numbers after send. The composer's `[&_pre]` utilities also override the node view's padding and paint a second background tint ([code-block-view.tsx:51-75](../apps/web/src/components/chat/composer/code-block-view.tsx); [style.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/core/src/style.ts)). The fix is one shared typography token set applied to both `.ProseMirror` and `.message-markdown`. No palette change is needed.

## Each keystroke re-renders 1,838 lines and runs four view updates

TipTap 3's defaults are already right: `shouldRerenderOnTransaction` is off and `immediatelyRender` is on ([upgrade guide](https://tiptap.dev/docs/guides/upgrade-tiptap-v2); [useEditor.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/react/src/useEditor.ts)). Lor's own subscriptions undo them. Three `useEditorState` selectors each do work proportional to the document. One calls `getText()` on the whole document, one walks `doc.descendants` to collect mention IDs, and one runs five `isActive` checks plus code-block lookups ([message-input.tsx:926-953, 1244-1271](../apps/web/src/components/chat/composer/message-input.tsx)). The text value changes on every character, so **`MessageInput` re-renders on every keystroke**. The selectors are inline arrow functions, and `useSyncExternalStoreWithSelector` memoizes on selector identity, so all of them also run again during every render.

Each of those renders then does more editor work. `useEditor` compares `extensions` by reference and `editorProps` with `!==` ([useEditor.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/react/src/useEditor.ts)). The composer builds `StarterKit.configure(...)`, `Mention.configure(...)` and a fresh `editorProps` inline, so the comparison always fails. **`editor.setOptions()` runs after every render**, and it calls `view.setProps()` and then `view.updateState()`: two full ProseMirror update passes ([Editor.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/core/src/Editor.ts)). `<BubbleMenu>` receives inline `shouldShow`, `options`, `appendTo` and `getReferencedVirtualElement` props. Its effect therefore **dispatches an extra transaction after every render** ([BubbleMenu.tsx](https://github.com/ueberdosis/tiptap/blob/main/packages/react/src/menus/BubbleMenu.tsx)). That transaction re-runs every selector and plugin. The hidden menu still renders four buttons, and each runs an `editor.can()` command chain. Each update also triggers a full `getJSON()`, `JSON.stringify` and a synchronous `localStorage.setItem`, with no debounce. The total per content keystroke is about four ProseMirror update passes, three `getText` calls, three or four document walks and one complete React render of an unmemoized subtree. That subtree includes framer-motion's `AnimatePresence`, popovers and, in sessions, the model and effort pickers.

The host makes this worse in sessions. `MessageInput` is not wrapped in `React.memo`, and hosts pass new closures. Lor stream frames call `queryClient.setQueryData` once per frame with no throttle ([use-lor-stream.ts:214-238](../apps/web/src/hooks/use-lor-stream.ts)). So **while Lor streams, every frame runs the whole sequence in the composer the user may be typing in**. Renders driven by `useSyncExternalStore` are synchronous and cannot be time-sliced. There is a subtler risk too. When stored marks are set, `updateState` clears an active composition ([prosemirror-view index.ts](https://github.com/ProseMirror/prosemirror-view/blob/master/src/index.ts)). A background render during an IME composition that started after Cmd+B could therefore end the composition. That is plausible but unverified. TipTap's own guidance is that "the editor should be isolated from renders that don't affect it" ([TipTap performance guide](https://tiptap.dev/docs/guides/performance)). Keystroke latency is something users notice: 37signals cites about 4 ms per keystroke for Lexxy against 38 ms for Trix in a 10,000-word document ([Lexxy 1.0](https://dev.37signals.com/lexxy-1-0/)).

Code blocks add their own cost. The Shiki plugin caches tokens by node identity. The block being edited gets a new node on every keystroke, so it is **re-tokenized synchronously inside the plugin's `apply`** on every keystroke. Any document change also rebuilds the full `DecorationSet` for every code block instead of mapping the old one ([code-block-shiki.ts:74-118, 133-144](../apps/web/src/components/chat/composer/code-block-shiki.ts)). The block is a `ReactNodeViewRenderer`, so its Base UI `Select` re-renders on each keystroke inside it. The default `plaintext` language means that a block inserted from the `/` menu never highlights. TipTap fixed the same failure class in its lowlight extension in 3.32.3, where highlighting was "unnecessarily triggered by selection-only changes" ([TipTap releases](https://github.com/ueberdosis/tiptap/releases)). The cleaner architecture is decoration-based highlighting with a lazy parser, as in `prosemirror-highlight` ([ocavue/prosemirror-highlight](https://github.com/ocavue/prosemirror-highlight)). The required fixes are mechanical. Build the extension list once in a factory and route callbacks through refs. Hoist the BubbleMenu props. Move chrome into children with narrow selectors that return primitives; TipTap 3.20's `useTiptapState` is an option here. Memoize `MessageInput` with stable host props. Debounce drafts and flush them on blur and `pagehide`. All the costs above are unmeasured, so record a React Profiler trace and a Safari Web Inspector timeline before and after the change.

## Caret, focus and layout gaps make the desktop app feel like a web page

The macOS app runs on the system WKWebView, so ProseMirror treats it as Safari ([browser.ts](https://github.com/ProseMirror/prosemirror-view/blob/master/src/browser.ts)). Two upstream fixes are in range of the current specifiers. **prosemirror-view 1.42.9** (October 31) fixes "the editor could dispatch Enter or Backspace keys during composition" and a selection change "right after focus" being overwritten ([ProseMirror changelog](https://prosemirror.net/docs/changelog/)). TipTap 3.32.3 fixes bubble menus after IME input and a React warning when `setContent` creates React node views inside an effect, which is exactly what the draft restore does ([TipTap releases](https://github.com/ueberdosis/tiptap/releases)). The editor sets no `spellcheck`, `autocorrect` or `writingsuggestions` attributes. Another chat composer found that macOS WebKit "silently replaced ASCII apostrophes with smart quotes... corrupting prompts containing code or commands," and the substitution is gated by spellcheck ([OpenBitFun PR #3684](https://github.com/GCWing/OpenBitFun/pull/3684)). The `writingsuggestions="false"` attribute arrived in Safari 18 ([WebKit Safari 18](https://webkit.org/blog/15865/webkit-features-in-safari-18-0/)). One developer, though, reports that inline predictions kept breaking a contenteditable in a Mac WKWebView after every documented switch was set ([Apple forums 800476](https://developer.apple.com/forums/thread/800476)). The sound policy is spellcheck on for prose and off inside code blocks, with each switch confirmed on a device.

`DesktopCaret` is a sensible workaround for a real WebKit stale-caret problem ([WebKit bug 176896](https://bugs.webkit.org/show_bug.cgi?id=176896)). It hides the native caret and paints a 1 px span on the next animation frame. It has gaps. Its height is fixed at 16 px against 20 px and 24 px lines. Its soft-wrap affinity comes from a collapsed DOM range, which carries no affinity, so it is unverified. It hides on gap cursors, and TipTap paints its own gap cursor as `1px solid black`, which is **invisible in dark mode** ([desktop-caret.tsx:41-85](../apps/web/src/components/chat/composer/desktop-caret.tsx); [style.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/core/src/style.ts)). The edit box does not render it at all, so editing a message on desktop shows the native caret that has the stale-paint bug.

Focus handling falls short of the convention. Slack documents that "upon navigating to a conversation, your focus will land in the message composer" and that on Mac you simply start typing ([Slack screen reader help](https://slack.com/help/articles/360000411963-Use-Slack-with-a-screen-reader)). Its engineers explain why: "the next most likely action is that the user will type" ([Slack Engineering](https://slack.engineering/managing-focus-transitions-in-slack/)). Lor never autofocuses on a channel, thread or session switch. Clicks on the box padding do nothing. The New-session box has a 44 px dead zone below its 20 px editable ([message-input.tsx:1444-1486](../apps/web/src/components/chat/composer/message-input.tsx)). Attaching a connector record probably returns focus to the "+" button, because `handleAttachRecord`, unlike the Linear path, never sets the return-focus flag. Type-to-focus calls `preventDefault` and inserts `event.key` itself. That drops Option-composed characters, dead keys and the first IME key, and it always moves the caret to the end ([message-input.tsx:1178-1201](../apps/web/src/components/chat/composer/message-input.tsx)). The edit box focuses twice, with `autofocus` and again on a 200 ms timer, which can pull a caret the user just placed back to the end.

Layout is the last layer. StarterKit's TrailingNode adds an empty paragraph whenever the last node is not a paragraph. Typing `- `, inserting a code block or pasting a Linear card therefore **grows the composer by one phantom line** ([trailing-node.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/extensions/src/trailing-node/trailing-node.ts)). The 200 px scroller has no edge padding. In the session composer's 24 px line height it clips mid-line, at 8.3 lines. The reply bar and attachment row snap in height. In sessions the composer is now `sticky` inside the transcript scroller, and teammates' typing lines animate height inside that sticky block. Because the scroller reacts through a ResizeObserver followed by an animation frame, growth probably covers the last transcript line for one frame (unverified visually) ([session-document.tsx:690-772](../apps/web/src/components/session/session-document.tsx)). The bubble menu waits the plugin's default 250 ms. It anchors to the selection head rather than the range, and it listens only for window scroll, so it **detaches when the editor's own scroller moves** ([bubble-menu-plugin.ts](https://github.com/ueberdosis/tiptap/blob/main/packages/extension-bubble-menu/src/bubble-menu-plugin.ts)). Popups and the bubble menu mount on `document.body`, outside the CSS-zoomed desktop region, so at non-100% zoom they can render at a different scale. That is also unverified.

Chunks 1 to 3 remove the harms users already meet: rewritten edits, deleted text, ignored commands, keyboard dead ends and accidental @channel. Each is small and independent, so they can ship in any order after chunk 0. Chunk 4 is the hinge. It creates the shared factory, which also removes the `setOptions` churn, so the paste, markdown, link and layout chunks each add one extension to one list rather than editing two editors. Chunk 6 needs the most care: it changes what Shift+Enter builds. The alternative is to keep hard breaks and register duplicate input rules that accept the `%leaf%` sentinel. That works, but it depends on a TipTap internal, so this report recommends the paragraph model, which Campsite and Plane already ship. Joining paragraphs with hard breaks when serializing keeps stored markdown and rendered spacing as they are today. Whether `@tiptap/markdown` emits exactly the expected output for blank lines and joined paragraphs must be confirmed by hand, because the upstream hard-break bugs are still open.

Some product decisions sit outside the code and should be made before the chunks that depend on them. Chunk 6 needs a decision on blockquotes in the schema. Chunk 12 needs a decision on Cmd+K: scoping it to a composer selection follows Linear, Notion and GitHub, while Slack moved link to Cmd+Shift+U because Cmd+K is its switcher ([Slack shortcuts](https://slack.com/help/articles/201374536-Slack-keyboard-shortcuts); [Linear editor docs](https://linear.app/docs/editor)). Chunk 1 assumes underline is dropped, as in Campsite's chat schema, rather than rendered as `<ins>` ([Campsite chat.ts](https://github.com/campsite/campsite/blob/main/packages/editor/src/chat.ts)). Chunk 13 needs a decision on autocorrect.

Verification is manual QA in Chrome and the macOS Tauri app. Chunk 1 needs an edit-and-save matrix: bold, a list, a mention, a link, a fence and a Linear block, saved unchanged, must come back byte-identical. "C++ … i++" must survive, and `/pr_comments` must run as a command. Chunks 2 and 6 need the key table above, run in a paragraph, a nested list, a code block, a code block inside a list and multi-line messages. Chunk 3 needs "@", "@l" and "@e" + Enter, Backspace on a mention, and a stale menu followed by a click into the thread composer. Chunks 5 and 9 need React Profiler and Safari Web Inspector traces of typing while Lor streams and of typing at the top of a 300-line code block. Chunk 7 needs pastes from Claude.ai, ChatGPT, VS Code (in both browsers), a terminal, Google Docs and Notion, plus a 5,000-character log and a screenshot copied with text. ## Conclusion

The composer's problems come from coordination, not from the engine. Lor handles keys in three places (view props, capture listeners, keymaps), patches serializer output with regexes, positions popups by hand and rebuilds options on every render. Each of these duplicates something TipTap 3.32 now provides: extension priorities, per-node `renderMarkdown`, Suggestion's `mount` and memoized options. So the lasting asset of this work is the shared editor core from chunk 4. Once the channel composer, the edit box and the session composer run one extension list and one keymap, the edit box stops being a second, worse editor, and every later improvement reaches all three surfaces in one change.

The second takeaway is particular to an AI workspace. Lor's messages go to two audiences, people through a markdown renderer and agents and harnesses as text. The escaping that makes markdown render correctly is exactly what corrupts the text that agents read, as the `/pr\_comments` failure shows. Lor needs a deliberate two-output contract, rendered markdown for people and plain text for models and commands, rather than one string that serves both badly. Users also paste LLM output and code far more often than in Slack, so paste fidelity is a core feature for Lor, not a nicety. The open questions that remain are WebKit-specific, and only a hands-on QA pass in the desktop app can close them.
